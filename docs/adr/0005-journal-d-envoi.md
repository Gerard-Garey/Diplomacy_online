# Une réponse part sous un journal d'envoi écrit avant la requête ; un envoi incertain se résout par relecture des messages de la partie, jamais sur la foi d'une erreur

Consigne, après implémentation et visa, la règle du journal d'envoi (issue #5, volet de fond) que l'ADR 0004 renvoyait à un « ADR propre » (Conséquences, « Journal d'envoi (#5) »). Rédigé par `architect` (routage Fable, `docs/agents/routage.md` § 4.1.3 ; deuxième consultation Fable de la branche sur trois) à partir du code tel que visé, des décisions du mainteneur M17 et M36 (2026-10-03) et de celles du 2026-10-10 (PR #20). Le code est lu à `ab872ab`, tête de `claude/promesses` : les lignes citées sont celles de `cicero/overlay/claude_dialogue_bot.py` à ce commit, et les tests ceux de `tests/test_etat_dialogue.py`, classe `Envois` (48 tests, remesurés le 2026-10-10 : 48 exécutés, 0 échec, 0 échec attendu).

**Corrigé le 2026-10-10** (revue finale de la branche, `audit` ; texte corrigé en place, la règle ne change pas) : (1) décision 9, le décompte « douze tests `test_l_*` » était faux, `grep -c "def test_l_" tests/test_etat_dialogue.py` rend 10 ; (2) Contexte et option « renvoyer sur la foi d'une erreur », la phrase « tout ce qui peut échouer vient après l'INSERT » était inexacte : des écritures Redis et un contrôle de longueur précèdent l'INSERT (`gamemessage.php:62-76`) ; un échec antérieur au stockage est classé « incertain » comme un autre, la décision n'en dépend pas ; (3) une limite connue ajoutée (message de plus de 65 000 octets).

## Contexte

**Le constat de l'issue #5** (revue finale du 2026-10-03) : l'engagement sincère était écrit dans `pseudo_commitments.json` avant l'envoi du message, et `post_req` (amont, `fairdiplomacy_external/webdip_api.py:195-201`, commit épinglé de `versions.env`) rend la réponse HTTP sans lever sur un statut 4xx ou 5xx (lecture vérifiée : la fonction ne fait que `post(...)` puis `return resp`). Deux scénarios en découlaient : une erreur réseau laissait l'engagement enregistré pour un message jamais parti, et le cycle suivant engendrait une autre réponse ; une réponse 500 marquait le message répondu et comptait l'échange alors que le joueur n'avait rien reçu. Le critère d'origine de la tâche T7 (feuille de route, § 1.4) : « un envoi en échec ne laisse aucun engagement enregistré et ne marque pas le message comme répondu ; un message n'est jamais envoyé deux fois (exigence 5.3) ».

**Ce que fait le site** (`amont/webdiplomacy/api.php`, classe `SendMessage`, lignes 1651-1720, et `lib/gamemessage.php`, `libGameMessage::send`, lignes 60-110 ; lu, non exécuté, sauf l'essai d'envoi réel ci-dessous) :

- destinataire qui a coupé les messages de la puissance (`isCountryMuted`) : la route rend `{"messages": []}` avec le statut 200, sans rien stocker ;
- sinon `libGameMessage::send` refuse un message de plus de 65 000 octets (`gamemessage.php:62`, exception « Message too long »), écrit dans Redis l'heure du dernier message (`$Redis->set("lastmsgtime_…")`, `gamemessage.php:68-76` : quatre appels dans le source, dont deux exécutés pour un message à une seule puissance), écrit le message (`INSERT INTO wD_GameMessages`, `gamemessage.php:78`) **puis** notifie, déclenche l'événement Redis (`$Redis->trigger`, `gamemessage.php:95-102`), envoie une notification web push ; la route relit ensuite le message dans la table et le rend sous la clé `messages`. Un échec peut donc survenir **avant** l'INSERT (longueur, `$Redis->set` : rien n'est stocké) ou **après** lui (notification, `$Redis->trigger`, push, relecture, transport HTTP : le message est stocké, l'INSERT étant final dès qu'il s'exécute). Vu du bot, les deux se ressemblent : une requête qui a l'air d'avoir échoué peut avoir stocké le message, et le site ne fournit aucune clé d'idempotence. *(Corrigé le 2026-10-10 ; le texte d'origine disait : « Tout ce qui peut échouer (notification, Redis, push, relecture, transport HTTP) vient après l'INSERT ».)*

**Deux règles en tension.** L'invariant « l'état écrit sur disque l'est aussitôt » (`CLAUDE.md`, « Architecture ») et l'exigence 5.3 (« un message n'est jamais envoyé deux fois, y compris après le redémarrage d'un conteneur ») ne se satisfont pas ensemble par un simple réordonnancement : écrire l'engagement après l'envoi laisse une fenêtre où le message est parti et l'engagement perdu si le processus s'arrête ; renvoyer sur la foi d'une erreur produit un doublon quand l'INSERT a eu lieu. Question à cheval, posée séparément à `expert-cicero` (sens d'un engagement dont le message n'est pas parti) et à `expert-webdip` (statuts de l'API, `post_req`) ; circuit 1 (feuille de route, § 1.2).

**Décisions du mainteneur** : M17 et M36 (2026-10-03, feuille de route § 4) fixent la règle ; le 2026-10-10 (PR #20, « Décisions du mainteneur du 2026-10-10 »), il accepte les trois écarts au critère d'origine et donne son visa par la fusion de la PR #20 (`9ac8511`).

## Décision

Arrêtée par le mainteneur le 2026-10-03 (M17, M36), confirmée avec ses écarts le 2026-10-10 (PR #20). Chaque point renvoie au code et au test qui le réalisent.

1. **Ordre des écritures.** Une réponse à envoyer passe par quatre étapes, chacune persistée avant la suivante : (a) l'état `claude_dialogue_state.json` — `by_recipient` et `own_promises.pending` tels que la réponse les laisse, **plus** `pending_send`, qui dit ce qui part et comment le défaire (lignes 1622-1641) ; (b) le fichier d'engagements `pseudo_commitments.json` (`_apply_send_to_commitments`, appelée en tête de `post_pending_send`, ligne 1282) ; (c) la tentative comptée dans l'état (`attempts += 1` puis `checkpoint()`, lignes 1283-1284) ; (d) la requête (`post_req`, ligne 1294). Une tentative n'est comptée que si la requête est faite. Si (a) échoue, rien n'est écrit pour le moteur ni envoyé (`test_k_etat_illisible_a_l_etape_2`, `test_k_ecriture_de_l_etat_impossible_a_l_etape_2`) ; si (b) échoue, le bot se tait (`UnreadableStateFile`), `pending_send` reste à 0 tentative, et la réponse part au cycle où le fichier redevient inscriptible (`[send-resume]`, lignes 1349-1365 ; `test_c3_ecriture_des_engagements_impossible_a_l_etape_3`, douze cycles de panne, un seul envoi ensuite). L'ordre (a) puis (b) est vérifié pendant la requête même (`test_b_etat_puis_engagements_ecrits_avant_l_envoi`).
2. **Contenu du journal.** `pending_send` porte : `ts` (le message répondu, clé de `game.messages`, en chaîne), `recipient`, `text`, `phase`, `added` (`by_recipient` : ordres ajoutés pour ce destinataire ; `commitments` : ordres que le fichier d'engagements ne tenait pas encore), `removed` (ordre retiré et ses détenteurs, pour une trahison ou une révision), `own_pending` (clé et valeur antérieure de `own_promises.pending`), `journal` (lignes à annoncer, point 8), `attempts`, `rereads` (lignes 1622-1636). Un seul `pending_send` par bot et par partie (clé d'état `api_key:game_id`, ligne 1192).
3. **Classement de la réponse** (`_send_outcome`, lignes 918-943) : **confirmé** — statut 200, corps JSON de bout en bout, liste `messages` non vide dont le premier élément porte un `timeSent` entier ; **sourdine** — statut 200 et liste vide ; **incertain** — tout le reste (autre statut, corps vide ou non JSON, JSON suivi d'une page HTML, `timeSent` absent, exception levée par la requête, lignes 1296-1297). Seize cas dans `test_classement_de_la_reponse_du_site`.
4. **Suites immédiates** (`post_pending_send`, lignes 1276-1321). Confirmé : message marqué répondu, échange compté, marque ajoutée à `sent_ts`, `pending_send` effacé, état écrit, puis annonces (`confirm_send`, lignes 1254-1264 ; `test_a_envoi_confirme`). Sourdine : engagements de la réponse défaits dans le fichier puis dans l'état, message marqué répondu, échange **non** compté, ligne `[send-muted]` (`drop_send`, lignes 1266-1274 ; lignes 1304-1313 ; `test_g_sourdine`). Incertain : `pending_send` reste, rien n'est reposté sur-le-champ, ligne `[send-uncertain]`, et **le bot ne traite aucun autre message de cette partie** tant que l'envoi n'est pas résolu — ni réponse, ni extraction des promesses des interlocuteurs (`unsettled`, lignes 1642-1649 ; tête de cycle, lignes 1408-1411 ; `test_c_envoi_incertain` sur les quatre échecs en apparence, `test_extraction_ecartee_tant_que_l_envoi_n_est_pas_resolu`). Le blocage ne porte que sur ce bot dans cette partie : un autre bot de la même partie répond (`test_cloisonnement_un_envoi_incertain_ne_bloque_que_son_bot`).
5. **Résolution par relecture** (`settle_pending_send`, lignes 1323-1406), en tête de cycle, **avant** toute lecture, tout jugement ou tout rappel de promesse (lignes 1408-1411) : une promesse dont le message n'est pas connu pour être parti n'est ni jugée ni rappelée à Claude. Les messages envoyés par le bot sont lus dans le statut de la partie, toutes phases confondues (le site range un message dans la phase « Diplomacy » de son tour), avant `webdip_state_to_game` qui les efface du JSON (`_messages_sent_by`, lignes 871-889 ; lignes 1218-1219). Le message cherché est celui adressé au même destinataire, de même clé de texte (point 6), dont `timeSent` n'est pas antérieur à la seconde du message répondu, et qui n'est pas déjà comptabilisé dans `sent_ts` — une réponse identique envoyée plus tôt ne confirme pas celle-ci (`_find_pending_send`, lignes 896-915 ; `test_i_recherche_du_message`, onze cas ; `test_i_message_identique_anterieur_ne_confirme_pas`). Trouvé : ligne `[send-confirmed]`, engagements réappliqués (idempotent), `confirm_send` (lignes 1366-1377). L'état final est alors identique, octet pour octet, à celui d'un envoi confirmé d'emblée (`test_d_meme_etat_qu_un_envoi_confirme_d_emblee`), y compris quand l'état est rechargé du disque entre les cycles (`test_d_relecture_qui_confirme`, trois comportements du site × redémarrage).
6. **Clé de comparaison** (`_message_key`, lignes 824-836) : sauts de ligne unifiés (`\r\n`, `\r`, `<br />` → `\n`), entités HTML décodées, blancs extérieurs retirés, caractères au-delà de U+FFFF et « ? » retirés des deux côtés. La marque de `sent_ts` est `timeSent:destinataire:sha1(clé)[:16]` (`_sent_mark`, lignes 839-844), `timeSent` seul étant à la seconde. Tests `test_m_texte_avec_accents_et_balises`, `test_m_caractere_hors_plan_de_base`, `test_m_cle_de_comparaison` ; essai d'envoi réel aux Conséquences.
7. **Deux relectures négatives, puis renvoi du même texte** (`SEND_REREADS_BEFORE_RETRY = 2`, ligne 54 ; lignes 1378-1392). Première relecture négative : `rereads` incrémenté et écrit, ligne `[send-pending]`, rien d'envoyé. Seconde, si la phase est la même et `attempts < MAX_SEND_ATTEMPTS` : `rereads` remis à 0, ligne `[send-retry]`, et `post_pending_send` reposte `ps["text"]`, inchangé (`test_e_relecture_negative_puis_renvoi_du_meme_texte` : deux envois de texte identique, un seul message sur le site ; `test_e_au_renvoi_etat_et_engagements_sont_sur_disque`). Le compteur de relectures est sur disque à l'étape même : un processus tué après la première relecture repart d'elle (`test_e_compteur_de_relectures_ecrit_a_l_etape_meme`). Décision de prudence de la session principale, signalée au mainteneur (M36) : une seule relecture suivrait de trop près une requête qui a pu stocker avec retard.
8. **Abandon.** Après `MAX_SEND_ATTEMPTS = 3` envois (ligne 50) et deux relectures négatives du dernier, ou dès que la phase a changé (ligne 1387 ; lignes 1393-1406 ; jamais posté et phase changée : lignes 1353-1361), `drop_send` défait les engagements de la réponse — dans le fichier puis dans l'état, une promesse retirée étant rendue à **tous** ses détenteurs (`_undo_send_in_commitments`, lignes 991-1004 ; `_undo_send_in_state`, lignes 1007-1029) —, marque le message répondu (`replied_ts.add`, ligne 1272), ne compte pas l'échange et imprime `[send-failed]` une fois, au cycle où l'annulation est écrite (`test_f_abandon_annonce_une_fois_l_annulation_ecrite`). Déroulé remesuré : envois aux cycles 1, 3 et 5, abandon au cycle 7 (`test_f_plafond_atteint`) ; à `POLL_INTERVAL_SECONDS = 60` (ligne 34), sept cycles font six minutes de scrutation au moins, plus la durée des cycles eux-mêmes. Un message stocké est confirmé même après le changement de phase (`test_f_phase_changee_mais_message_stocke`) ; l'abandon après une trahison acceptée rend la promesse trahie à ses deux détenteurs et ramène l'état à celui d'avant le message (`test_l_abandon_apres_une_trahison_acceptee`).
9. **Annonces différées, au plus une fois.** Les lignes qui annoncent un changement d'engagement — `[betrayal]`, `[revision]`, `sincere commitments ->` — sont gardées dans `pending_send["journal"]` (lignes 1552-1578, 1633) et imprimées par `confirm_send` seul, après l'écriture de l'état (lignes 1263-1264) : un envoi en sourdine ou abandonné n'en imprime aucune, un envoi confirmé à un cycle ultérieur les imprime à ce cycle, et une panne d'écriture à la confirmation les reporte sans les doubler (`test_l_trahison_confirmee_par_relecture`, `test_l_trahison_annoncee_une_fois_si_l_etat_ne_s_ecrit_pas_a_la_confirmation`, `test_l_reprise_*`, dix tests `test_l_*` — corrigé le 2026-10-10 : « douze » à l'origine, `grep -c "def test_l_" tests/test_etat_dialogue.py` rend 10). Les refus (`[double-deal]`, `[betrayal-refused]`, `[betrayal-ignored]`) ne changent rien et restent imprimés au jugement (lignes 1502-1544). C'est la décision 15 de l'ADR 0004, réalisée par ce journal.
10. **Réponse vide avec `sincere` non vide** (`NO_REPLY_TOKEN`) : rien n'est retenu ni écrit pour le moteur, le message est marqué répondu, aucun envoi (lignes 1608-1614 ; `test_j_reply_nul_avec_sincere`, le fichier d'engagements gardant ses octets). Ligne 0 de la table de décision de #17 (M17).
11. **`pending_send` mal formé** (`_valid_pending_send`, lignes 946-970 ; la clé `journal` peut manquer — état écrit avant qu'elle existe —, sinon elle est une liste de chaînes) : il ne peut être ni confirmé ni défait. Le message qu'il répondait est marqué répondu si son `ts` se lit encore (chaîne de chiffres, ou entier écrit à la main) ; sinon une ligne `WARNING` dit qu'il pourra être répondu une seconde fois ; rien d'autre n'est défait (lignes 1326-1348 ; M36 ; `test_pending_send_mal_forme_ecarte`, `test_pending_send_mal_forme_message_stocke_jamais_renvoye`, `test_pending_send_mal_forme_ts_entier_message_stocke_jamais_renvoye`, `test_validite_du_journal_d_un_pending_send`).
12. **`sent_ts` abîmé** : ce qui n'est pas une marque est retiré avec une ligne `[sent-ts]`, la partie n'est pas bloquée (`_sent_ts`, lignes 847-868 ; `test_sent_ts_abime`).
13. **Trois écarts au critère d'origine, acceptés par le mainteneur le 2026-10-10** (PR #20) :
    1. *L'engagement est lisible par le moteur pendant l'incertitude d'un envoi*, jusqu'à sept cycles (point 8) : le fichier d'engagements est écrit avant la requête (point 1) et n'est défait qu'à l'abandon. Pendant ce temps le moteur peut renforcer un ordre dont le message n'est peut-être pas parti ; il ne fait que le renforcer en probabilité (ADR 0003, décision 4), jamais en valeur.
    2. *Le message est marqué répondu à l'abandon* (ligne 1272) : il ne reçoit pas de seconde réponse, et l'échange n'est pas compté.
    3. *Le risque de doublon n'est pas nul* : un renvoi après deux relectures négatives (point 7) double le message si le site l'a stocké après la seconde relecture, rien côté site ne bornant ce retard (commentaire des lignes 51-54). Cas non exercé, ni par un test ni sur la pile.

## Options écartées

- **Enregistrer l'engagement après l'envoi confirmé** (formulation antérieure de l'issue #17 et de la feuille de route, § 1.1, remplacée au cours de la branche) : un processus arrêté entre la requête et l'écriture perd l'engagement d'un message pourtant parti, et il faut de toute façon savoir, au redémarrage, ce qui était en cours d'envoi ; le journal écrit avant la requête donne cette mémoire et respecte « l'état écrit sur disque l'est aussitôt ». C'est l'écart 1.
- **Renvoyer sur la foi d'une erreur** (reposter dès un statut 5xx ou une exception) : une partie de ce qui peut échouer côté site vient après l'INSERT (Contexte ; corrigé le 2026-10-10, « l'INSERT précède tout ce qui peut échouer » à l'origine), si bien qu'un renvoi immédiat double le message chaque fois que l'échec est postérieur au stockage ; c'est le cas que les comportements `*_STOCKE` du faux site reproduisent et que l'exigence 5.3 interdit.
- **Ne jamais renvoyer** (un seul envoi, abandon dès l'incertitude) : le joueur ne recevrait pas la réponse à la première erreur réelle (500 sans stockage), et l'engagement serait défait pour un message que Claude a pourtant écrit ; M17 retient trois envois du même texte. Raison reconstituée à la rédaction de l'ADR : l'option n'a pas été débattue comme telle le 2026-10-03.
- **Renvoyer après une seule relecture négative** : une relecture faite un cycle après la requête (60 s) suit de trop près une écriture qui a pu être retardée ; M36 porte le seuil à deux (décision de prudence de la session principale, signalée au mainteneur). Le prix est un cycle de plus avant chaque renvoi.
- **Marquer le message non répondu à l'abandon** (critère d'origine) : Claude écrirait une nouvelle réponse au cycle suivant, qui ferait un second message si le premier avait été stocké avec retard, et qui relancerait le compte des dix échanges par paire et par phase ; marquer répondu borne le dommage à une réponse perdue. C'est l'écart 2.
- **Différer l'écriture de `pseudo_commitments.json` à la confirmation** : pendant l'incertitude, le moteur ignorerait une promesse peut-être déjà reçue par le joueur et pourrait jouer contre elle ; et l'information pour défaire serait nécessaire de toute façon. L'écart 1 est le côté choisi : la promesse faite est tenue pour faite jusqu'à preuve du contraire.
- **Clé d'idempotence côté site** (patch de `SendMessage` ajoutant un identifiant de requête) : un patch d'amont sur la route de l'API, à porter à chaque changement de commit épinglé, pour un cas résiduel ; écarté à la rédaction de l'ADR, non débattu le 2026-10-03. Rouvrir si l'écart 3 est observé en partie.
- **Confirmer par `timeSent` seul** : résolution d'une seconde ; deux messages au même destinataire dans la même seconde seraient confondus, d'où la marque `timeSent:destinataire:empreinte` (lignes 839-844).
- **Défaire un `pending_send` mal formé, ou répondre de nouveau au message** : on ne sait ni ce qui a été écrit ni si le message est parti ; défaire pourrait retirer une promesse réellement envoyée, répondre de nouveau pourrait doubler. M36 : marquer répondu, ne rien défaire.
- **Continuer à traiter les autres messages de la partie pendant l'incertitude** (file d'envois) : les réponses suivantes seraient écrites par Claude avec, dans la consigne, une promesse peut-être jamais partie, et l'extraction jugerait des conversations incomplètes ; un seul `pending_send` par bot et par partie, et rien d'autre tant qu'il n'est pas résolu (point 4), au prix d'un bot muet dans cette partie pendant sept cycles au plus.

## Conséquences

- **Résultats changés** (visa du mainteneur par la fusion de la PR #20, `9ac8511`, 2026-10-10 ; « avant » = `claude/promesses` à `7372dcf`) : le moment où un engagement atteint le moteur (avant la requête, sous journal) et son retrait quand le message n'est pas parti ; le contenu de `sincere` retenu (réponse vide : rien ; sourdine ou abandon : défait) ; le marquage et le décompte des échanges (envoi incertain : ni l'un ni l'autre tant que l'envoi n'est pas résolu ; abandon : marqué, non compté) ; le journal (lignes `[send-…]`, annonces différées). Mesures : banc déterministe et faux site (`tests/faux_site.py`), tests cités point par point ci-dessus ; tableau par issue dans la passation de la PR #20 (commentaire du 2026-10-03), section #5. La mesure d'`audit` « 0 doublon sur 3 844 scénarios exhaustifs et 1 200 essais aléatoires » est reprise de cette passation et **non remesurée** ici (script d'audit non versionné).
- **Essai d'envoi réel** (protocole `tests/mesure/envoi_reel.md`, partie jetable n° 4, supprimée ensuite ; traces hors git `amont/mesure/resultats/m4_envoi_4.json` et `m4_comparaison_4.json`, relues le 2026-10-10) : statut 200, classé `sent` ; accents et `&`, `<` relus en entités, le saut de ligne en `<br />`, **l'émoji stocké `????`** (quatre « ? », un par octet) ; message retrouvé une fois par la clé. La clé tolère ces quatre cas (point 6). Fait **une fois**. Le commentaire de `_message_key` (ligne 831, « not verified ») et le faux site (un « ? » par caractère) décrivent l'hypothèse d'avant l'essai : à mettre en concordance avec l'observation (retouche sans effet sur un résultat, hors de cet ADR).
- **Contrats partagés.** `claude_dialogue_state.json` reçoit, par bot et par partie, les clés `pending_send` (point 2) et `sent_ts` (liste de marques, point 6). Un état sans ces clés se lit comme sans envoi en attente ; un `pending_send` sans `journal` est admis (`test_l_pending_send_d_avant_le_journal_confirme_sans_annonce`). Le format de `pseudo_commitments.json` ne change pas ; le **moment** de son écriture change (point 1).
- **Invariants de `CLAUDE.md`.** « L'état écrit sur disque l'est aussitôt » : respecté à chaque étape (`checkpoint()` après chaque mutation, lignes 1197-1212). « Le moteur décide, le dialogue informe » : l'engagement lisible pendant l'incertitude (écart 1) n'agit que sur la probabilité. « Cloisonnement » : un `pending_send` par bot et par partie, et le blocage ne touche que ce bot dans cette partie. Aucun invariant n'est modifié.
- **Exigence 5.3** (« un message n'est jamais envoyé deux fois, y compris après le redémarrage d'un conteneur ») : garantie **à relecture près** — jamais sur la foi d'une erreur, jamais sans relecture préalable, et le redémarrage est couvert (`pending_send` sur disque avant la requête ; `test_c1_etat_illisible_pendant_l_envoi_un_seul_message`, `test_d_relecture_qui_confirme` avec redémarrage) ; mais l'écart 3 subsiste. Le texte de l'exigence est à rouvrir par le mainteneur ; formulation proposée : « 5.3. Un message n'est jamais renvoyé sur la foi d'une erreur : un envoi incertain est d'abord relu dans les messages de la partie, y compris après le redémarrage d'un conteneur ; un renvoi après deux relectures négatives peut encore doubler un message que le site aurait stocké avec retard (ADR 0005, écart 3). »
- **ADR 0004.** La décision 15 (balises après confirmation) et le paragraphe « Journal d'envoi (#5) » des Conséquences renvoient ici ; rien n'y change. L'ADR 0003 (décision 3, « elle seule est transmise au moteur ») reste exact : ce qui atteint le moteur est toujours `pseudo_commitments.json`.
- **Limites connues**, sans changement de code dans cette branche :
  - *Annonce quand la confirmation vient d'un nouvel envoi* (`[send-retry]`, `[send-resume]`) : relevé par l'audit du 2026-10-10 comme non couvert par un test. Mesuré **une fois à la main** par `architect` le 2026-10-10, avec le montage de `tests/test_etat_dialogue.py` et le scénario de trahison : dans les deux cas les trois annonces sortent une fois au cycle de la confirmation et zéro fois au cycle suivant, un seul message sur le site. Comportement conforme au point 9, **non protégé** : test à ajouter (`coder` → `audit`, circuit 3, aucun résultat changé).
  - *Essai d'envoi réel fait une fois*, un texte, une partie jetable ; ni le statut 500 ni la sourdine n'ont été observés sur le vrai site (reproduits par le faux site d'après la lecture du code d'amont).
  - *Doublon résiduel* (écart 3) : non exercé ; aucune borne connue au retard de stockage.
  - *Première entrée seulement* : `_send_outcome` lit `messages[0]` (ligne 940) ; la route ne rend que le message qui vient d'être écrit (relecture par `timeSent`, expéditeur et destinataire), ce qui suffit, mais deux messages du même bot au même destinataire dans la même seconde seraient rendus ensemble — cas théorique, non traité.
  - *Bot muet pendant l'incertitude* : jusqu'à sept cycles sans réponse dans la partie pour ce bot ; observable par le joueur comme un silence.
  - *Message trop long* (ajouté le 2026-10-10) : `libGameMessage::send` lève « Message too long » au-delà de 65 000 octets (`gamemessage.php:62`, lu), avant tout stockage. Le statut que l'API rend alors n'est **pas mesuré** ; s'il n'est pas un 200 bien formé, l'envoi est classé « incertain » (point 3), le même texte est envoyé trois fois puis abandonné (point 8), sans doublon possible puisque rien n'est stocké. Aucune borne de longueur de `reply` n'a été trouvée dans `claude_dialogue_bot.py` (recherche par `grep`, pas une preuve d'absence) ; aucune réponse de cette taille n'a été observée.
- **Textes à rouvrir** : `docs/doc/architecture.md` § 4 (journal d'envoi, lignes `[send-…]`, annonces différées ; déjà listé par l'ADR 0004, `docwriter` en fin de branche) ; `docs/exigences.md` 5.3 (mainteneur, texte proposé ci-dessus) ; `CONTEXT.md`, « Journal d'envoi » et « Sourdine » (entrées existantes, renvoi à cet ADR ajouté).
- **Ce que l'ADR ne règle pas** : une clé d'idempotence côté site ; la borne du retard de stockage ; le cas d'un message adressé à tous (`toCountryID` 0 : non examiné ici) ; l'isolement par partie d'un fichier d'engagements mal formé (#22 : un bot muet par `UnreadableStateFile` laisse son `pending_send` à 0 tentative, point 1, et reprend à la réparation) ; la purge des clés `sent_ts`, qui croissent d'une marque par message envoyé (à voir avec #11).
